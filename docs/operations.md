## 2. なぜ GitHub Actions が動いていないのか

### 原因1: コードが `main` ブランチに無い
GitHub Actions の定期実行（`schedule`）は、**デフォルトブランチ（main）にあるワークフローしか実行しません。**

現在の状態:
```
main                                    ← README.md のみ
claude/referral-nurturing-strategy-...  ← 全コードはこちら（未マージ）
```

GitHub上の登録ワークフロー数: **0件**（確認済み）

### 原因2: `package-lock.json` が無い
ワークフロー内の `npm ci` は `package-lock.json` を必須とします。現在このファイルが存在しないため、
マージしても最初のステップで失敗します。

### 原因3: ワークフローが `main` に直接 push する設計
`git push origin main` を含むため、ブランチ保護設定によっては失敗します。

### 稼働させるために必要なこと
1. `npm install` を実行して `package-lock.json` を生成・コミット
2. このブランチを `main` にマージ（PR経由）
3. リポジトリ設定 → Actions → 「Read and write permissions」を有効化
4. 初回は手動実行（Actions タブ → workflow選択 → Run workflow）で動作確認

**これらは未実施です。ご指示をいただければ対応します。**

| Cloudflare Pages | ¥0 | 可 | ◎ | 高速・解析機能あり。推奨 |

## 4. Indeed / 求人ボックス 応募の自動取込

### 重要な前提

**Indeed も求人ボックスも、スプレッドシートにデータを送る機能はありません。**
API連携も、一般的な採用企業アカウントでは提供されていません。

実際に自動化できる経路は1つです:

```
応募発生
  ↓
Indeed/求人ボックスから「応募通知メール」が届く
  ↓  （info@careerjapan.co 等の受信ボックス）
Apps Script が Gmail を検索してメールを解析
  ↓
スプレッドシートに自動追記
```

これを実装したのが `01-media-ingest.gs` です。

### 設定手順

**STEP 0: スクリプトを開く**
1. 求人媒体スプシ（`15B9X9...`）を開く
2. 拡張機能 → Apps Script
3. `00-diagnose.gs` `01-media-ingest.gs` `02-nurturing.gs` の3ファイルを貼り付け

**STEP 1: シート構成を確認（書き込みなし・安全）**
```
関数 shindan() を実行
```
実行ログに全タブ名と列構成が出ます。応募を書き込みたいタブ名を控えてください。

**STEP 2: タブ名を設定**
`01-media-ingest.gs` の以下を書き換え:
```javascript
TAB_NAME: '',   // ← ここに STEP1 で確認したタブ名を入れる
```
※空欄のままだと安全装置が働き、実行が中止されます。

**STEP 3: 応募メールを調査（書き込みなし・安全）**
```
関数 chosa_ouboMail() を実行
```
実行ログに、実際に届いている応募メールのサンプルと、そこから氏名・電話番号を
抜き出せているかが表示されます。

- **該当0件の場合** → メールが別アカウントに届いている可能性。`query` の調整が必要
- **抽出結果が空の場合** → `PARSE_PATTERNS` の調整が必要（ログの本文を見て正規表現を修正）

この結果を共有いただければ、パターンを実際のメール形式に合わせて修正します。

**STEP 4: 試験実行（書き込みなし）**
```
関数 torikomi_TEST() を実行
```
「何件取り込まれるか」だけが表示されます。スプシは変更されません。

**STEP 5: 本番実行**
```
関数 torikomi_HONBAN() を実行
```
実際にスプシへ追記されます。処理済みメールには「取込済み」ラベルが付き、二重取込を防ぎます。

**STEP 6: 自動化**
```
関数 triggerSettei() を実行
```
15分おきの自動取込が有効になります。

### 重複防止
電話番号の下10桁で既存レコードと照合します。既に存在する応募者は追記されません。

## 5. ナーチャリング自動化（キャリカミ等の面談管理）

`02-nurturing.gs` を使います。対象は広告面談スプシ（`1wEKLJ...`）です。

### 設定手順

**STEP 1:** `shindan()` でタブ名を確認

**STEP 2:** `NURTURE_CONFIG.TAB_NAME` に求職者一覧のタブ名を設定

**STEP 3:** スクリプトプロパティを設定
プロジェクトの設定 → スクリプト プロパティ → 追加:

| プロパティ名 | 値 |
|------------|-----|
| `SLACK_WEBHOOK_URL` | SlackのIncoming Webhook URL |
| `EMAIL_MATSUMOTO` | 松本さんのメールアドレス |
| `EMAIL_ARAKI` | 荒木さんのメールアドレス |
| `EMAIL_GOSHI` | 合志さんのメールアドレス |

※未設定でも動きますが、その分の通知はスキップされます（ログには出ます）

**STEP 4:** `kakunin_TEST()` で試験実行
- 現在の温度感分布（Hot/Warm/Cold比率）
- Hot判定された求職者の一覧
- 通知先の設定状況

が表示されます。**メール・Slackは一切送信されません。**

**STEP 5:** `nurtureTriggerSettei()` で自動化を有効化

### 稼働後のスケジュール

| 時刻 | 処理 | 通知先 |
|------|------|--------|
| 8:00 | 本日・明日の面談リマインダー | Slack + 担当CAへメール |
| 10:00 | Hot判定チェック | Slack + 担当CAへメール |
| 15:00 | Hot判定チェック（再） | Slack + 担当CAへメール |
| 18:00 | 日次KPIレポート | Slack |

### 温度感スコアの算出根拠

実際のスプシ列から計算します（最大100点）:

| 項目 | 配点 |
|------|------|
| 希望就職時期（今すぐ=35 / 1〜2ヶ月=26 / 3〜4ヶ月=14 / 5ヶ月=6） | 35 |
| フェーズ（選考中=30 / 求人提案=22 / 面談実施=14 / 面談設定=8） | 30 |
| 承認/否認が「〇」 | 15 |
| 面談実施が「〇」 | 10 |
| 正社員経験（3年以上=10 / それ以外の経験あり=5） | 10 |

**Hot = 55点以上**（`NURTURE_CONFIG.HOT_THRESHOLD` で調整可能）

「その他離脱」「求人紹介不可」のフェーズは全て集計対象外です。

## 6. 承認フローについて

### 現在の状態
**承認すべきものは何も生成されていません。**（GitHub Issue: 0件）

### 稼働後の承認フロー（§2 の対応が完了した場合）

1. 毎朝9時、GitHub Actions がニッチサービスを生成
2. リポジトリの **Issues** タブに承認依頼が自動作成される
   - URL: `https://github.com/matsumoto-ayuta-hub/recruitment-agency/issues`
   - タイトル例: `🚀 承認依頼: 中卒から介護士への転職エージェント`
   - 松本さんが自動アサインされ、GitHubから通知メールが届きます
3. Issue本文でLP内容・ターゲット・想定インパクトを確認
4. 承認する場合 → **Issueのコメント欄に `approved` と入力して送信**
5. `approval-handler.yml` が反応し、ステータスをLiveに更新してIssueをクローズ

### 注意点
現在の `approval-handler.yml` は「ステータスをJSONで更新してIssueを閉じる」までしか行いません。
**実際のWeb公開処理は含まれていません**（§3のホスティング先が未定のため）。
公開先が決まり次第、デプロイ処理を追加します。

## 7. セキュリティに関する指摘

求人媒体スプシ（`15B9X9...`）の1枚目のタブに、各媒体（Indeed・求人ボックス・engage 他）の
**ログインIDとパスワードが平文で記載されています。**

このスプレッドシートは編集権限が共有されている可能性が高く、以下のリスクがあります:
- 共有リンクが外部流出した場合、求人媒体アカウントが乗っ取られる
- 退職者がアクセス権を保持し続ける
- Apps Script の権限経由で第三者スクリプトから読み取られる

**推奨対応:**
1. パスワード管理ツール（1Password / Bitwarden など）へ移行
2. スプシからは削除、またはアクセス権を松本さんのみに制限
3. 主要アカウントの2要素認証を有効化

※コード・リポジトリには一切記録していません。
