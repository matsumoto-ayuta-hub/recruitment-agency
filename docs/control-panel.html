01

最優先で知っておくべきこと

今日サイトを調べて分かったことです。LLMO戦略の前提が崩れる内容なので、最初に共有します。

corekara.info は、AI検索から中身が一切見えていません

現在のサイトは JavaScript で画面を組み立てる作りです。ブラウザでは正常に見えますが、HTMLそのものには本文が1文字も入っていません。実際に取得した中身がこれです。

<body> <div id="root"></div> ← 本文がここに無い </body> JavaScriptを実行しない場合に読めるテキスト量： 54文字 （タイトルとメタタグのみ。会社概要も求人情報もゼロ）

何が起きるか：ChatGPT・Perplexity・Claude などの検索クローラーは、多くの場合 JavaScript を実行しません。つまり今のままニッチLPを毎日作っても、AIには白紙のページとして扱われます。

言い換えると：LLMO対策のコードは書けていますが、それを載せる土台がまだ機能していない状態です。ドメインの話と一緒に解決すべき最重要課題です。

補足：これは外注先の手抜きとは限りません。React等で作ると標準でこうなります。ただ「AI検索で戦う」なら作り方を変える必要があります。
02

ドメインの判断

「.info は安く見えて企業信頼性に繋がらない」という感覚は正しいです。そのうえで、調べた事実を踏まえた選択肢を並べます。

調査結果

  • corekara.info … 稼働中。Firebase Hosting 配信。メタ情報の作者名は「株式会社CAREER JAPAN」
  • careerjapan.co … Webサイトとしては未設定（Aレコードなし）。メールでは稼働中なので、ドメイン自体は保有済み
  • 応募実績は累計 1,758件。ただし .info ドメイン自体の検索評価はもともと高くありません
案構成企業信頼性LLMO適性移行コスト
A 現状維持 corekara.info のまま 低低（評価が分散）なし
B 併用 会社 = careerjapan.co
サービス = corekara.info		 中低（2ドメインに分散し最も不利）小
C 統合 推奨 careerjapan.co に集約
corekara.info は301転送		 高高（1ドメインに集中）中

C案を推す理由

  • AI検索の評価はドメイン単位で蓄積します。毎日ニッチLPを増やす戦略は、全部を1つのドメイン配下に置いたときに最も効きます
  • 今ならコンテンツ量が少なく、移行コストが最小です。記事が100本溜まってからでは遅い
  • 「コレカラ転職」はサービス名として careerjapan.co/corekara の形で残せます。ブランドを捨てる必要はありません
  • 301リダイレクトを正しく設定すれば、既存の評価と流入は引き継げます
重要：ドメイン移行だけでは 01 の問題は解決しません。移行と同時にSSR（サーバー側で本文を生成する作り）に変えるのが正解です。別々にやると二度手間になります。
03

今日の作業：Apps Script 再設定

関数を全削除いただいたので、ゼロから手順を書き直しました。所要 25分ほど。STEP 1〜4 はスプレッドシートに一切書き込みません。

  1. 1

    スクリプトの置き場所を作る

    script.google.com を開き、左上「新しいプロジェクト」をクリック。プロジェクト名は「CareerJapan 自動化」など分かりやすい名前に。

    左メニューのファイル横「＋」から 3つのファイルを作り、GitHubの中身をそれぞれ貼り付けます。

    FILE00-diagnose01-media-ingest02-nurturing
    なぜ独立プロジェクト？スプレッドシートが2つあるため、どちらかに紐付けると混乱します。独立させれば両方を安全に扱えます。
  2. 2

    シート構成を確認する書き込みなし

    上部の関数選択メニューから shindan を選び「実行」。初回は権限の承認画面が出ます。

    「このアプリは Google で確認されていません」と表示されたら、「詳細」→「（プロジェクト名）に移動」と進んでください。ご自身が書いたスクリプトなので問題ありません。

    確認すること：下部の「実行ログ」に両スプレッドシートの全タブ名と列構成が出ます。この内容をそのままコピーして私に送ってください。正しいタブ名が分かれば次に進めます。
  3. 3

    書き込み先のタブ名を設定する

    STEP 2 で確認したタブ名を、2つのファイルにそれぞれ入力します。

    01TAB_NAME: '応募管理'← 求人媒体の応募を書き込むタブ
    02TAB_NAME: '求職者一覧'← キャリカミ等の面談管理タブ
    安全装置：ここが空欄のままだと、すべての処理が実行前に停止します。前回のような誤ったタブへの書き込みは起きません。
  4. 4

    Indeed・求人ボックスの応募メールを調べる書き込みなし

    chosa_ouboMail を実行します。Gmailに届いている応募通知メールを検索し、そこから氏名・電話番号を取り出せるかテストします。

    ここが自動化の成否を分ける一番重要な工程です。メールの書式は媒体ごとに違い、実物を見ないと正確に読み取れません。

    確認すること：実行ログに出るメール本文のサンプルと「抽出テスト」の結果をそのまま私に送ってください。実際の書式に合わせて解析部分を書き直します。
    「該当0件」と出た場合：応募メールが別アカウント（info@ など）に届いている可能性があります。どのアドレスに届いているか教えてください。
  5. 5

    今の温度感を見てみる通知は飛びません

    kakunin_TEST を実行。既存の面談データから Hot / Warm / Cold の比率と、今すぐ連絡すべき求職者の一覧が出ます。

    メールもSlackも送信されないので、安心して試せます。目標50%に対して現在何%なのか、ここで初めて実数が分かります。

    確認すること：Hot判定された方の顔ぶれを見て、感覚と合っているか教えてください。ズレていれば点数の配分を調整します。
  6. 6

    通知先を登録する

    左メニュー「プロジェクトの設定」→ 下部「スクリプト プロパティ」→「プロパティを追加」。

    KEYSLACK_WEBHOOK_URLEMAIL_MATSUMOTOEMAIL_ARAKIEMAIL_GOSHI

    Slack は「アプリ → Incoming Webhooks」から発行できます。未設定でも動きますが、その分の通知は飛ばず実行ログに残るだけになります。

  7. 7

    本番稼働させる

    STEP 4 の調整が終わってから実行してください。順番が大切です。

    順にtorikomi_TEST→torikomi_HONBAN→triggerSettei→nurtureTriggerSettei

    torikomi_TEST は「何件取り込まれるか」だけを表示します。件数が想定通りなら本番へ。

    稼働後のスケジュール：応募取込は15分おき／面談リマインド 8時／Hot判定 10時・15時／日次レポート 18時
    何かおかしいと感じたら：zenTriggerSakujo を実行すれば全自動処理が即座に止まります。
04

GitHub 側が止まっている理由

毎日のニッチサービス生成・LLMO更新・承認Issueは、現在1件も動いていません。原因は3つで、いずれも解消可能です。

原因内容対応
コードの置き場所 定期実行は main ブランチのファイルしか動きません。現在 main には README しかない状態です main へマージ
※ご承認が必要
依存ファイル欠落 package-lock.json が無く、実行の1行目で失敗します 私が生成します
公開先が未定 LPを作っても置く場所がなく、承認しても公開されません 02 の判断待ち

稼働後、承認はここで行います

GitHubリポジトリの Issues タブに毎朝9時、承認依頼が自動作成されます。松本さんに自動アサインされるので通知メールが届きます。内容を確認し、コメント欄に approved と入力して送信すれば承認完了です。所要2〜3分。
